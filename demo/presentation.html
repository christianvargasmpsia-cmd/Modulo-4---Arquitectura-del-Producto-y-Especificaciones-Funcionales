Decisiones Arquitectónicas

Architecture Decision Records (ADRs)

ADR-0001
Arquitectura Orientada a Eventos
✅ Aceptada
Contexto

Múltiples módulos críticos (pedidos, pagos, stock, notificaciones) necesitan coordinación desacoplada sin bloqueo síncrono ante alta concurrencia.

Decisión

RabbitMQ como Event Bus central. Pub/Sub para coordinación asíncrona entre microservicios con correlationId obligatorio.

  • Desacoplamiento total entre servicios
  • Resiliencia ante fallos parciales
  • Trazabilidad con correlationId
  • Mayor complejidad operacional
ADR-0002
Saga Pattern — Coreografía
📋 Propuesta
Contexto

El flujo pedido → pago → stock → notificación requiere transacciones distribuidas con compensación automática ante fallos parciales.

Decisión

Saga por Coreografía: cada servicio reacciona a eventos del bus y emite compensaciones. Sin coordinador central (sin SPOF).

  • Consistencia eventual garantizada
  • Compensación automática ante fallo
  • Sin Single Point of Failure
  • Debugging distribuido más complejo
ADR-0003
Arquitectura Hexagonal (Ports & Adapters)
✅ Aceptada
Contexto

La lógica de dominio (stock, pagos, pedidos) debe estar aislada de implementaciones de infraestructura (DB, API bancaria, MQ).

Decisión

Ports & Adapters: núcleo de dominio puro sin dependencias externas. Adapters intercambiables en infraestructura.

  • Dominio 100% testeable sin mocks
  • Intercambiabilidad de infraestructura
  • Cumple SOLID & Clean Architecture
  • Más abstracciones en la capa inicial

Diagrama de Secuencia

Flujo Completo: Pago QR Dinámico con Saga (Coreografía)

%%{init: {"theme": "dark"}}%%
sequenceDiagram
    actor Customer as Cliente UMSS
    participant PWA as React PWA
    participant GW as API Gateway
    participant OrderSvc as Order Service
    participant PaySvc as Payment Service
    participant InvSvc as Inventory Service
    participant QRBank as API Bancaria QR
    participant Bus as RabbitMQ
    Customer->>PWA: Confirmar compra
    PWA->>GW: POST /api/v1/orders (JWT Bearer)
    GW->>OrderSvc: Crear pedido
    OrderSvc->>InvSvc: GET /internal/stock/{product_id}
    InvSvc->>InvSvc: Reserva optimista Redis TTL=300s
    InvSvc-->>OrderSvc: 200 OK stock disponible
    OrderSvc->>Bus: Publish ORDER_CREATED {order_id, total, correlationId}
    Bus->>PaySvc: ORDER_CREATED
    PaySvc->>QRBank: POST /qr/generate {amount, reference, callback_url}
    QRBank-->>PaySvc: qr_url · qr_id · expires_in=300
    PaySvc->>Bus: Publish PAYMENT_PENDING {order_id, qr_url}
    Bus->>OrderSvc: PAYMENT_PENDING → estado QR_GENERADO
    PWA-->>Customer: Mostrar QR countdown 5 min
    Note over Customer,QRBank: Cliente escanea QR con su app bancaria móvil
    QRBank->>PaySvc: POST /webhooks/payment {webhook_ref, amount, hmac_sha256}
    PaySvc->>PaySvc: 1. Validar firma HMAC-SHA256
    PaySvc->>PaySvc: 2. Verificar idempotencia webhook_ref único
    PaySvc->>PaySvc: 3. Verificar monto == Pedido.total exacto
    PaySvc-->>QRBank: HTTP 200 OK
    PaySvc->>Bus: Publish PAYMENT_CONFIRMED {order_id, correlationId}
    Bus->>InvSvc: PAYMENT_CONFIRMED
    InvSvc->>InvSvc: UPDATE qty = qty - N WHERE qty >= N (atómico)
    InvSvc->>Bus: Publish STOCK_RESERVED {order_id, qty}
    Bus->>OrderSvc: STOCK_RESERVED → estado CONFIRMADO
    OrderSvc->>Bus: Publish ORDER_CONFIRMED {order_id}
    PWA-->>Customer: Pedido confirmado!
    Note over InvSvc,Bus: Compensación: si TTL 300s expira antes del pago
    InvSvc->>Bus: Publish STOCK_RELEASED
    Bus->>OrderSvc: STOCK_RELEASED → estado CANCELADO
    PWA-->>Customer: QR expirado — pedido cancelado
